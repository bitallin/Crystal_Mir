# 0016 以 VERA20K 为参照的会话边缘与可验证性边界

- 状态：提议
- 日期：2026-11-19

## 背景

对 `https://www.ra20k.com/` 和 `YuriPlanet/vera20k` 的公开资料做了架构对标。目标项目是 Rust 重写的《红警2/尤里的复仇》RTS 平台，采用确定性模拟、HTTPS 大厅、认证 UDP relay、WebAssembly/跨平台客户端和内容寻址的 UGC 地图/Mod 供应链。

Crystal 是持久世界传奇 MMO，现有优势是成熟游戏逻辑、服务端权威、内容快照与签名发布、后台编辑、RBAC、审计、Zone Agent 和客户端事务更新。两者不能做整体架构替换。

当前 Crystal 的主要缺口是：

- 登录、选角、进服和游戏仍在同一 TCP 连接，缺少独立会话边缘和节点目录。
- 客户端只校验版本哈希，缺少 protocol/client/content/rules/map 的多维开局协商。
- 没有实例化房间/匹配/观战/回放服务。
- 没有玩家 UGC 地图/Mod 的独立供应链。
- 客户端与 WinForms/Direct3D9 耦合，跨平台演进困难。
- 玩家运营面与管理员控制面没有分离。

详细对标见 `docs/architecture/08-vera20k-benchmark-and-refactor.md`。

## 决策

### 1. 保留服务端权威 MMO 模型

Crystal 的持久世界、经济、交易、掉落和角色资产继续由 ZoneServer 权威裁决。不采用 VERA20K 的“客户端保留 simulation authority + relay 排序命令”作为 MMO 主模型。

### 2. 新增会话边缘，不替换旧协议

新增 MIT 的玩家会话与边缘网关边界，负责玩家认证、会话 token、节点路由、限流、公开配置和版本门禁。旧客户端继续走现有 TCP 路径；新客户端通过可选预会话握手接入。网关第一版不解析全部游戏包，只处理必要的登录/版本状态和透明转发。

### 3. 增加多维开局协商

在现有客户端版本哈希之外，逐步引入：

- `protocol_version`
- `client_version` / `build_id`
- `content_schema_version`
- `content_hash`
- `rules_hash`
- `map_hash`
- `capabilities`

不兼容时返回结构化升级错误和下载入口；具体包格式、兼容窗口和回退路径由后续协议 ADR 规定。

### 4. 把可验证性限制在实例化玩法

在主世界增加只追加命令日志和周期状态摘要，支持审计、客服和回放。实例化 PvP 可以先做服务端权威的 command journal + replay；在解决浮点、线程和随机源之前，不承诺客户端确定性重演或 lockstep。

### 5. UGC 与官方内容分域

新增内容寻址的 UGC 地图/Mod 供应链，拥有独立的版本、审核、举报、下架和下载票据。官方签名内容包与 UGC 包使用不同信任级别，不共享发布状态机。UGC 内容不得携带未经授权的原版游戏资源。

### 6. 玩家面与管理面分离

- `Crystal.Control.Api` 继续服务版本作者、管理员、审计和 Zone Agent。
- 新增玩家会话/门户边界，服务账号、区服列表、公开统计、房间、排行和 UGC。
- 两者可以共享 PostgreSQL 基础设施，但使用独立 schema、权限模型和限流策略。

### 7. 学契约，不盲目引入产品

VERA20K 前端使用 Nakama 兼容契约。Crystal 只借鉴其“会话 + 命令游标 + 事件游标 + 功能开关”的契约形态，不因此把 Nakama 引入控制面，也不改变现有 .NET/PostgreSQL 技术栈。

## 备选方案

1. **整体对齐 VERA20K**：把服务端世界重写为 Rust 确定性模拟，客户端权威 + relay。适合短局 RTS，不适合持久 MMO，成本和风险不可接受，拒绝。
2. **只复制前端和官网**：视觉和玩家流量入口会改善，但不解决会话、版本、UGC 和客户端边界，拒绝。
3. **继续只做管理后台**：内容治理会继续增强，但玩家侧入口、匹配、UGC 和版本运营仍缺失，拒绝。
4. **直接引入 Nakama**：可以快速获得社交/排行榜能力，但增加第二套状态后端和权限模型；当前 .NET 控制面已能承载，推迟。
5. **先抽 ClientCore、不重写渲染**：保留 WinForms 交付能力，同时为未来跨平台保留边界，接受。

## 影响

- 新增玩家会话、Gateway、UGC 和 ClientCore 四个边界，需要独立契约和测试。
- 旧客户端在一段时间内继续直连；新能力通过可选握手和功能开关逐步开放。
- 区服启动/进服会增加内容、规则和地图摘要校验。
- 实例 PvP 的房间服务不能直接修改角色资产；结果必须回写权威区服。
- 需要新的玩家面 schema、节点目录、对象存储和审核流程。
- 跨平台渲染不在本决策内自动启动，避免范围失控。

## 回滚/重新评估条件

- 如果预会话握手无法在旧协议上保持兼容，回退到透明 TCP 网关，只保留节点路由和限流。
- 如果 command journal 对主循环性能影响超过预算，降级为采样日志并只在实例玩法启用。
- 如果 UGC 审核成本高于收益，先只开放官方精选地图，不开放玩家上传。
- 如果 ClientCore 抽离不能降低客户端改动风险，暂停跨平台渲染评估。
- 如果产品明确要求浏览器版完整游戏，再单独评估 MatchCore、确定性和渲染重写。
