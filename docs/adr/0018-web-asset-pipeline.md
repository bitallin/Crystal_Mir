# 0018 Web 资源编译与版本化

- 状态：已接受
- 日期：2026-11-19

## 背景

现有客户端从本地 `Data/`、`Map/` 和 `Sound/` 读取 `.lib` 图库、`.map` 地图和音效。浏览器不能依赖本地路径，也不适合在运行时解析旧的 `.lib`/`.map` 二进制格式。直接请求原始素材会造成体积、解析和缓存问题。

## 决策

- 新增平台无关的 `Crystal.WebAssets` 和 `tools/Crystal.WebAssetCompiler`，离线把客户端素材转换为 Web 资源包。
- `.lib` 转换为带帧偏移、遮罩、阴影信息的纹理图集和 `frames.json`；不要求浏览器运行时解析 `.lib`。
- `.map` 转换为小型 `meta.json` 和紧凑 `cells.bin`，包含地图尺寸、地图库引用、后/中/前层索引、可走性、门、光照和动画信息。
- 顶层 manifest 记录资源版本、内容哈希、地图/图库/音效索引和文件哈希；资源 URL 使用不可变缓存，地图和角色库按需懒加载。
- 资源编译器必须确定性输出：同一输入和版本生成相同文件与哈希；缺少必要素材时失败，不生成半成品。
- Web 客户端与服务端内容按兼容组合发布；客户端在资源版本或关键文件哈希不匹配时阻断进入。
- 按当前研究项目口径，现有素材可直接转码作为外部输入；不开展授权/商业化合规，素材和生成物不提交仓库。GPL/MIT 代码边界仍按 `adr/0004-gpl-boundary.md` 执行。

## 备选方案

1. 浏览器运行时直接加载 `.lib`/`.map`：需要移植解析器、增加首包和移动端内存开销，且难以为地图做懒加载。
2. 只使用原始图片和地图文件：缺少帧偏移、遮罩、地图层和碰撞元数据，无法复现客户端表现。
3. 重制全部美术：质量和版权最可控，但成本和周期不适合首版垂直切片。

## 影响

- 资源发布成为独立步骤，需要与区服内容版本绑定并纳入 CI/部署。
- 纹理图集页面、地图二进制和音效格式需要在目标浏览器上做回归和内存测试。
- 旧客户端继续使用原始素材，不依赖 Web 资源包。

## 重新评估条件

- 纹理图集尺寸或移动端显存成为瓶颈，需要改用分块纹理、压缩纹理或按需流式加载。
- 资源需要进入控制面正式发布流程，而不是研究部署的静态产物。
