# 0017 原生浏览器客户端与 WebSocket 网关

- 状态：已接受
- 日期：2026-11-19

## 背景

当前 `Client/` 是 `net8.0-windows7.0` 的 WinForms 客户端，渲染依赖 SlimDX/Direct3D9，UI 是自绘控件树。浏览器不能直接复用这套运行时；同时现有区服用自定义 TCP 二进制协议承载登录、选角和游戏包。

目标是在不重写服务端权威逻辑的前提下，让玩家通过现代桌面和移动浏览器直接进入同一区服。

## 决策

- 新增独立原生 Web 客户端 `web-client/`，使用 TypeScript、Vite、PixiJS v8 和 Preact；它与旧 Windows 客户端并存，不替换旧入口。
- 新增 `Crystal.Web.Gateway`，每个浏览器 WebSocket 对应一条到区服的 TCP 连接，原样转发 `Shared` 定义的二进制包流。
- 网关不解析或改写游戏业务包，不链接 `Server/`、`Server.MirForms/` 或 WinForms；只做连接、Origin、限流、帧上限、背压、超时和指标。
- 首版单区服路由；WebSocket 接口保留 `zone` 参数和 `crystal-v1` 子协议，后续可在网关增加区服目录和会话票据。
- 首版沿用现有游戏账号和密码：登录包经 WSS 传到网关后原样转发；HUD 不持久化密码，网关不记录包体。
- 服务端保持权威；客户端只做表现层预测、输入采样和动画插值，不引入客户端权威或锁步模拟。
- 浏览器基线为最新两个版本的 Chrome/Edge/Firefox/Safari、iOS Safari 16.4+ 和 Android Chrome 110+；要求 WebGL2 和 `DecompressionStream`，不支持时显示阻断提示。

## 备选方案

1. 把 WinForms 客户端嵌入浏览器：不可行，依赖 Windows、SlimDX 和桌面窗口，无法在移动端运行。
2. 云游戏串流：原型快，但 GPU、带宽、并发和运维成本高，不适合作为长期主路线。
3. 新建 JSON/MessagePack 游戏协议：接口更现代，但需要长期维护双协议映射；首版复用现有二进制协议风险最低。

## 影响

- 客户端是独立代码库，需要独立构建、资源版本和测试矩阵；无法自动继承 WinForms 的 UI 行为。
- Web 资源与服务端内容必须按兼容组合发布；资源缺失或版本不匹配必须阻断并提示，而不是静默降级。
- 网关成为新的公网入口，必须限制 Origin、连接数、帧大小和速率，并避免记录账号密码和游戏包体。
- 旧客户端、旧协议和服务端游戏逻辑保持不变；破坏性协议变更仍按 `adr/0003-legacy-protocol-with-gateway.md` 处理。

## 重新评估条件

- 需要支持 WebGL2 之外的旧浏览器，或移动端性能无法达到验收门槛。
- 需要多区服路由、跨区会话、票据 SSO 或原生客户端统一登录。
- 现有二进制协议无法安全地映射到 WebSocket 边缘，或包体规模超过网关预算。
